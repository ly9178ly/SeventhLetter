# 《未寄出的第七封信》需求说明 v0.1

日期：2026-11-14。本文在业务代码开发前提交，后续变更单独记录。

## 目标与范围

使用 DevEco Studio、ArkTS、ArkUI 独立开发一款离线校园悬疑互动叙事应用。玩家在旧图书馆调查六封未寄出的信，通过搜证、对话与推理决定第七封信的收件人。结尾偏心理恐怖，保留人为操纵与超自然解释的歧义；游戏条件必须明确、可复现。

第一阶段：主页 → 图书馆 → 第一封信 → 条件选项 → 自动保存 → 退出应用后继续；同时提供证据档案、手动存档和可扩展剧情引擎。

完整目标：四个探索地点、三名角色、六封信及相关关键证据、约 18–24 个叙事节点、四个结局、证据组合推理、结局收集。完整目标不代表第一阶段已经完成。

## 模块与验收

| 编号 | 模块 | 用户行为与验收条件 |
| --- | --- | --- |
| R01 | 主页/导航 | 新调查、继续调查、证据档案、调查记录可进入；无存档时继续不可用 |
| R02 | 探索与对话 | 节点文字、地点、选项来自剧情数据；点击合法选项更新节点与状态 |
| R03 | 线索条件 | 未取得第一封信时关键提问锁定；获得后解锁；重复搜查不重复增加证据 |
| R04 | 证据档案 | 显示已收集证据及全文、来源；未获得证据不泄露正文 |
| R05 | 本地存储 | 每个有效选择持久化；手动保存可用；关闭进程后恢复节点、证据、选择历史 |
| R06 | 可靠性 | 坏档或不支持版本有提示；不静默覆盖；保存失败允许重试 |
| R07 | 推理与结局 | 后续阶段实现证据组合和四结局；达成条件有可复现测试 |
| R08 | 交付 | GitHub 有真实提交、中文 README、环境与运行步骤、真实截图/交互录像、测试记录及报告 |

## 架构与个人职责

独立完成，所有模块由本人负责，在 AI 辅助下设计、编码、验证和整理交付材料。不得编造团队成员、运行截图、测试结果或提交历史。

依赖方向：ArkUI 页面/自定义组件 → 调查会话服务 → 纯逻辑引擎与剧情数据；会话服务 → 存储接口 → Preferences 适配器。

| 目录 | 职责/接口 |
| --- | --- |
| `model` | Node、Choice、Evidence、GameState、SaveEnvelope 等显式类型 |
| `data` | 剧本文本、节点图与证据定义；无界面/设备依赖 |
| `engine` | 创建初始状态、检查条件、执行选择、校验存档；纯函数，非法选择不改变状态 |
| `storage` | 键值存储接口、Preferences 实现、存档编解码与版本校验 |
| `pages` / `components` | 页面导航、统一视觉组件、加载/错误反馈，不在 UI 内编写剧情规则 |
| `src/test` | 正常、边界、异常测试与 Mock 存储 |

## 数据与接口约定

- GameState：schemaVersion、nodeId、evidenceIds、flags、history、updatedAt。
- Choice：id、label、target、所需证据、所需 flags、获得证据、设置 flags。选项条件先校验再转换。
- Evidence：id、title、subtitle、source、body。
- Node：id、chapter、location、title、paragraphs、choices。
- `createGame()`：返回新状态；`canChoose(state, choice)`：返回可用性；`choose(state, choiceId)`：返回成功/失败及新状态。
- `StoragePort`：异步 read/write。`SaveRepository`：load/save，统一进行 JSON、schema、节点与证据合法性检查。

使用本地 Preferences 保存单个自动存档，不上传玩家选择；写入后 flush。状态包含版本号，坏档不作为有效存档加载。重开前明确确认；第一次启动无存档不误报损坏。后续可增加手动槽、备份和迁移。

## 一个月实施与改进计划

1. 第 1 周：可编译工程、首个探索闭环、证据与持久化、引擎和 Mock 测试。
2. 第 2 周：补齐四地点、人物、六封信与推理；校对故事线和四个结局。
3. 第 3 周：视觉、动效、无障碍、异常恢复、真机/模拟器实测。
4. 第 4 周：从新下载的工程复现构建，录制交互、完成报告与答辩准备。

每次迭代检查：功能是否能通过真实操作复现 → 边界/异常是否合理 → 文案和视觉是否清晰 → 记录实际发现和修复。
